# Admin UI (`app/admin/`)

Vanilla-JS SPA, **no build step**: `index.html` + one `css/style.css` + four JS files. `app/main.py` mounts `/admin/css` and `/admin/js` as StaticFiles and serves `index.html` with `{{BASE_PATH}}` substituted from `settings.root_path`, so edits are live on the next hard-refresh — no restart, no rebuild. Because the whole `js/` directory is mounted, adding a file needs no `main.py` change — only a `<script>` tag in `index.html`.

- `js/app.js` — shell, shared helpers, and most sections.
- `js/usage_report.js` — the API Usage Report section only. Loads **after** `app.js` and relies on its globals (`api()`, `esc()`, `toast()`, `currentUser`, `syntaxHighlight()`, `registerCopyPayload()`/`copyPayload()`). It exists as a separate file because `app.js` had already grown past 2000 lines and this section is self-contained.
- `js/mcp_tools.js` — the MCP Tools section only, same split and the same dependency on `app.js` globals.
- `js/write_definitions.js` — the Write Definitions section only, same split. It mirrors SQL Definitions' three full-page views (`enterWdView()`, two-pane grouped list, detail, form) and, unlike SQL Definitions, re-renders itself on a DB selector change (it adds its own `change` listener on `#dbSelect`).

Conventions inside `app.js`:

- `navigateTo(page)` maps a sidebar `data-page` key to a `render*()` function and a title; every page renders its HTML into `#contentArea`.
- Shared helpers: `api(method, path, body)` (auth header + error unwrapping), `dbPrefix()` (current `/{alias}` segment), `esc()` for **all** interpolated values, `toast()`, `openModal()/closeModal()`.
- Most sections use modals for create/edit; **SQL Definitions, Write Definitions and API Usage Report are the exceptions** — their list/detail views are full pages via `enterSqlDefView()` / `enterWdView()` / `enterUsageView()`. Follow the neighbouring section's pattern rather than mixing both in one section.
- **SQL Definitions' list view is a two-pane `.split-list`**: groups on the left sorted by name, the selected group's definitions on the right sorted by name. Grouping is on `group_name` (free text on the definition), **not** on `permission`. `GET /{db}/queries/definitions` returns registry order, so **both orderings are imposed client-side** in `renderSqlDefs()`. `sqlDefGroup` holds the selection across a detail round-trip and is reset when the current database has no such group; `paintSqlDefGroups()` / `paintSqlDefTable()` repaint the panes without refetching. An empty `group_name` is valid and buckets under `SQL_DEF_UNGROUPED`.
- **The definition detail page carries an MCP freshness note, and it is load-bearing.** Editing SQL is live; adding/renaming/deleting a definition or changing its metadata only reaches an LLM when the MCP client reconnects (`mcp_server/README.md` → Freshness). Without the note, an operator who fills in "Returns" and sees the LLM still reading the old description reports a bug. Keep it on the page the save flow lands on — `viewSqlDef()`, not the form.
- **`result_description` (the form's "Returns" field) has no consumer inside the Hub.** Nothing renders it except the definition detail page, and nothing validates it against the real result set — its only real reader is `mcp_server/catalog.py::build_description`, which puts it on a `Returns:` line in the MCP tool description. Do not "clean up" the field as unused, and do not add validation that would reject a value the operator meant as prose.
- **The create form derives Name and Permission from the Group.** `applySqlDefGroupPrefix()` keeps `<group>_` at the front of Name, `syncSqlDefPermission()` keeps Permission at `query:<name>`. Both are one-way: `sqlDefPrefix` / `sqlDefAutoPerm` record what the code last wrote, so once the user edits either field by hand it is never rewritten. Permission left empty still auto-generates server-side — the prefill only makes that value visible.
- **The Query Console picker and the SQL Definitions list hit the same endpoint with different intent.** `qcLoadDefinitions()` passes `?permitted_only=true` (the picker exists to be run from, so an entry the caller cannot execute only buys them a 403); `renderSqlDefs()` must **not**, or definitions would vanish from the page that maintains them. Superusers pass every check, so both look identical to an admin — a filtering bug here is only visible when testing as a role-limited user.
- **Write Definitions' dry run always sends `dry_run: true`**, whatever the textarea says — `dryRunWriteDef()` overwrites it. The button exists to test a payload against real data; it must never be a way to commit one. The page is superuser-only like the CRUD API behind it (`#navWriteDefs` is hidden in `showApp()`).
- **API Usage Report and MCP Tools are superuser-only.** `showApp()` hides `#navUsageReport` / `#navMcpTools` for everyone else; the backend's `get_current_active_superuser` remains the authority.
- **MCP Tools is read-only by design.** It reports the tool names the MCP server derives, including definitions it silently drops on a name collision. It configures nothing — the MCP server is a separate process driven by `MCP_*` env vars, so there is nothing here to write to. Do not grow it into a settings page.
- **Login page has two paths.** `window.__SSO_ENABLED__` (injected by `admin_spa()` alongside `{{BASE_PATH}}`) decides whether `#ssoBlock` is unhidden; the password form is always present so a broken isap-auth never locks admins out. `consumeSsoFragment()` runs first in the `DOMContentLoaded` handler, reads `#sso_token=` / `#sso_error=` left by `GET /api/v1/auth/sso/callback`, and clears it with `history.replaceState` so the JWT does not survive a reload. The `SSO_ERRORS` keys must stay in sync with the `sso_error=` slugs in `app/api/v1/auth.py`.
- **`api()` renews before it gives up.** A 401 triggers one `ssoRefresh()` (`POST /auth/sso/refresh`, `credentials: 'same-origin'`) and one replay of the request; only a second 401 falls through to `showLogin()`. The same call runs at boot when no JWT is in localStorage, so a returning user with a live SSO cookie never sees the login page. It is a no-op unless `window.__SSO_ENABLED__`. Keep it to a single retry — the refresh token rotates on every use, and a retry loop against a dead session just burns rotations.
- **Users list shows one account-type badge** (`accountTypeBadge()`): Service wins over SSO wins over Local, because a service account's `auth_source` is always `local` and printing it would be noise. The create form keeps the Authentication select and the Service-account checkbox in sync — checking Service forces `auth_source` back to `local` and re-enables the password field.
- **Password reset is its own dialog** (`openResetPasswordModal`), never a field on Edit User, and the row button is hidden for SSO accounts. A form containing a password input is a login form to a password manager: it fills that input and, needing a username to pair with it, overwrites the first text field — silently replacing another user's Full Name with the operator's own login. `autocomplete="off"` does not stop Chrome; removing the password field from that form does. Do not add one back.
- **Storage keys are scoped by base path** (`hub_token@/apihub`, `hub_current_db@/apihub`). localStorage is keyed by origin, and `/apihub` and `/apihub-test` share one — an unscoped key meant signing into either deployment silently signed you out of the other, and stomped its selected database too. A one-time migration adopts the old shared key and deletes it. Read `TOKEN_KEY`/`CURRENT_DB_KEY`, never the literal name (the e2e specs use a `readToken()` helper for the same reason).
- Playwright specs in `tests/e2e/` cover the Query Console, raw-JSON copy buttons, the API Usage Report, Write Definitions and the SSO login surface; run them after non-trivial Admin UI changes.
